# Quality and supply-chain policy

This project treats protocol input, lifecycle state, migrations, and command
boundaries as untrusted-input surfaces. The policy is deliberately measurable
and bounded so quality checks remain useful on every pull request.

## Ownership and gates

The `fmt`, `clippy`, `test`, `deny`, `shear`, and `db` jobs in
`.github/workflows/ci.yml` are required repository gates. CI owns execution;
the author owns fixing failures; an independent reviewer owns semantic review.
The database gate owns migration application and rollback-safe integration
coverage. No coverage percentage is a required check.

- `fmt`: `cargo fmt --all -- --check` (10 minute job limit).
- `clippy`: all workspace targets/features with warnings denied (20 minutes).
- `test`: workspace `cargo nextest` (25 minutes).
- `deny`: advisory, license, source, and duplicate-version policy (10 minutes).
- `shear`: unused dependency detection (10 minutes).
- `db`: PostgreSQL migrations and database tests (20 minutes).

Coverage is generated by the informational `coverage` workflow (35 minute
limit, 14-day artifact retention). It has no threshold and cannot replace a
required gate. The scheduled/manual `mutation` workflow is likewise
informational: it only mutates `push-receiver`, `rustplus-client`, and
`rustplus-adapter`, uses two workers, 20-second test timeouts, and a 45-minute
job limit. A mutation report is a review signal, not a merge gate.

## Parser and property testing

Representative `proptest` suites exercise MCS framing, Web Push authenticated
record rejection, camera ray ingestion, and Rust+ push pairing parsing. Their
properties are panic-freedom, bounded output/allocation, and the distinction
between incomplete input (wait for more bytes) and malformed input (typed
rejection). Tests MUST NOT merely encode then decode the same implementation.

## Dependencies and lockfile

- `Cargo.lock` is committed and reviewed with every dependency update.
- Renovate groups compatible Cargo patch/minor updates, opens lock-file
  maintenance weekly, and pins GitHub Actions to immutable full commit SHAs.
- New dependencies require a documented maintenance/correctness benefit,
  current upstream metadata review, and `cargo tree -d` inspection.
- `cargo deny check` enforces advisories, allowed licenses, registry/git source
  restrictions, and warns on duplicate versions. `deny.toml` is the single
  source for exceptions; every exception needs an owner, reason, upstream issue,
  expiry/review date, and the narrowest possible package scope.

## Vulnerability response and upgrade SLA

Maintainers monitor `cargo deny` advisories and Renovate alerts. A reachable
critical vulnerability receives triage within one business day and a patched
release or documented mitigation within seven calendar days. High severity is
triaged within two business days and upgraded or mitigated within 14 days;
medium/low findings are handled in the next planned dependency cycle (30/90
days
respectively). A vulnerability affecting an exposed production boundary may
pause releases even when the advisory is not yet a CI failure.

Reports MUST NOT include credentials, push payloads, database URLs, or tokens
in issues or logs. Use the repository's private security-reporting channel
when one is available; otherwise contact maintainers directly with the minimum
reproduction and no secret material. The response owner records affected
versions, mitigation, fixed version, and disclosure timing.

## Releases and provenance

A SemVer `v*` tag push or a maintainer-triggered release dispatch builds the
pinned Rust toolchain, a source archive, and the Linux binary. The release
workflow publishes SHA-256 checksums, an SPDX SBOM, and GitHub artifact
provenance using `id-token: write` and `attestations: write`, granted only to
the attesting job. It has no pull-request trigger and never grants write tokens
or production secrets to untrusted code.

**Tag protection is not currently enforced.** This repository is private on the
GitHub Free plan, where the rulesets API returns HTTP 403, so `v*` tags cannot be
restricted to maintainers. Compensating controls in the workflow: the tag must
match a strict SemVer pattern, checkout uses `refs/tags/<tag>`, and the build
fails unless the tag's commit equals the checked-out `HEAD`. Anyone with push
access can still create a tag and obtain an attestation for it, so consumers
MUST verify that the attested commit is on `main`. Enabling tag rulesets
(GitHub Pro/Team, or a public repository) is tracked for the next hosting-plan
review.

Artifact names are stable: `xiao-source-${tag}.tar.gz`,
`xiao-${tag}-x86_64-unknown-linux-gnu.tar.gz`, `SHA256SUMS-${tag}.txt`, and
`xiao-${tag}.spdx.json`. The OCI deployment path owned by issue #8 uses its
caller-supplied immutable `name:tag@sha256:digest`; when that image is promoted,
its digest and source commit SHOULD be attested using the same GitHub
attestation identity. This issue intentionally does not edit `deploy/` files.

## Exceptions and unavailable controls

A failing required gate is not waived by this document. If a GitHub-plan
control (required checks, branch protection, resolved conversations, or private
security intake) is unavailable, maintainers record the limitation in the PR,
keep the CI gate and independent semantic/security review, and schedule the
control for the next hosting-plan review. Exceptions to dependency policy use
`deny.toml` metadata and an expiry; expired exceptions fail review and MUST be
removed or renewed with evidence.
